The main site file lives in the site-generation/ folder not the main portfolio-site repo root. 
So to get it to work, in the terminal, from the repo root, change directory to site-generation, then run the commands npm install, npm run dev (starts the local dev server), and npm run build.

The part 1 option I chose was the theme picker (option A). The theme picker will change the presentation of the site mainly with CSS through chagning root variables of from the tokens.css file but the actual interaction invloving JS allows for the user to switch their theme preference on the header of the site on all pages and the selector uses js to add an attribute to the html tag, affecting the whole page. Also to keep the theme when leaving the page or reloading, when the theme is chagned, it will save the theme-preference to the local storage, allowing for the site to stay your chosen theme.
If JS is not available or if localStorage is not available, the site will default to your system default theme, and the theme selector will not be visible. While not making the theme picker usable sets the site to what you set your system theme to.
Also for part one, I added another js file to run while the site is first being rendered by the browser. This file is much smaller and only looks for the theme preference in the local storage so it does not take much to run so it should not cause the load to be slow, while the main them picker js file is deferred so that the enitre site could be loaded first then the interactive feature can be loaded later.

For the web component, I added a custom element called <github-activity> which fetches and displays a user's recent public GitHub activity. The endpoint of the fetch is https://api.github.com/users/{username}/events/public?per_page={count} where the useranme and count are set as attributes in the custom element, in my site the username will be set to my user of course and the count is set to 5, the count will determine how many activities will be fetched and displayed. For example an entry would look like: Pushed user/repo 55 days ago. If the script does not work or JS is not available, the content inside the custom element will bee displayed instead,in my site it will tell you its unable to load and gives a link to my profile directly. Also if the values put in the attributes are invalid like a non existent user or not a number for count it will also display the content in the custom element. The tag used would look like, 

<github-activity username="someone-random" count="5">
  <p>
    Unable to load recent activity right now - 
    <a href="https://github.com/someone-random" target="_blank">view my GitHub profile directly</a>.
  </p>
</github-activity>
<script src="/js/github-activity.js" is:inline defer></script>


The SSG I chose to use was Astro, it helped by allowing me to keep a basic layout for the head, header, nav, and footer layout throughout all of the pages (eithout adding them for each page, therefore removing them), meaning I only had to add the main content in each page. Also for the data-driven collection part, the static site generation seems very helpful to use, since all you have to implement is the data then the ssg will form the page for you, this made me remove the descriptions in the subpages for portfolio and add individual pages for each site, which would improve performance as I add more projects to the site. Even though this is helpful, it took a while to learn about the Astro API and about how to write stuff in .md and .astro though they are similar to HTML in some aspects, also how they all connect got very confusing and took a while to decipher and eventually work. The SSG also made the scoping confusing since I had to reorganize the files in a certain way which made my links to files different and I had to play around with it to get it to work. I would not use SSGs for more app oriented sites, where an interactive dynamic app is the main feature of the site, since the prepared layout would be helpful, the app itself would not need a lot of pages anyways so the SSG would not be necessary. Also if the site itself has pages but the pages all vary on layouts making it hard to maintain a template throughout the site, making the SSG not as helpful.
